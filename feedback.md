## 2. Modelos de Django (Backend)

**Lo que esta bien:**
- Modelo `Usuario` extiende `AbstractUser` con email como campo de autenticacion (elimina `username`) - excelente decision
- UUIDs como primary keys en todos los modelos - buena practica para APIs publicas
- `UsuarioManager` personalizado con `create_user` y `create_superuser`
- Relacion `Perfil` OneToOne con `Usuario` con `related_name='perfil'`
- `Habilidad` como M2M a traves de `Perfil` con `related_name='perfiles'`
- `Experiencia` vinculada a `Perfil` con cascade delete y ordering por `-fecha_inicio`
- Enum `TipoUsuario` con `TextChoices` (freelancer, cliente, ambos)
- `PublicacionManager` con metodos `activas()` y `por_categoria()` - buen uso de custom managers
- Indices en `Publicacion`: `(estado, -created_at)` y `categoria` - mejora consultas frecuentes
- `ImagenPublicacion` con `upload_to` dinamico y campo `orden`
- `JSONField` para `incluye` - apropiado para listas de texto variable
- Todos los modelos tienen `__str__`, `verbose_name` y `verbose_name_plural`

**Que mejorar:**

### 2.1 Campo `imagen_url` redundante con `ImagenPublicacion`
`publicaciones/models.py` linea 37: `imagen_url = models.URLField(blank=True)` coexiste con el modelo `ImagenPublicacion`. El frontend en `adapters.ts` linea 31 tiene que hacer fallback entre ambos: `item.imagenes?.[0]?.url || item.imagen_url`. Deben usar una sola fuente de imagenes.

### 2.2 Metodo `actualizar_perfil` nunca usado
`usuarios/models.py` lineas 88-91: el metodo `actualizar_perfil` en `Perfil` no se usa en ningun lugar del codigo. El serializer maneja las actualizaciones directamente. Es codigo muerto.

### 2.3 Funcionalidades core ausentes en `main`
El proyecto se llama "Marketplace de Servicios Profesionales" pero en la rama `main` faltan modelos fundamentales:
- **Contratos/Propuestas**: No hay modelo de contratacion. El frontend de contratos usa datos mock hardcodeados (`features/contracts/data.ts`)
- **Resenas**: No hay modelo de resenas. Los componentes `ReviewCard.tsx` y `ReviewsSummary.tsx` existen pero `rating` y `reviews` siempre son 0 (`adapters.ts` lineas 25-26)
- **Chat/Mensajeria**: No hay modelos de mensajeria en `main`

**Nota:** Vi que la rama `feat/chat-contratos` tiene implementados modelos de `Propuesta`, `Contrato`, `Conversacion` y `Mensaje` con buena calidad de codigo (UUIDs, TextChoices, relaciones correctas, `@transaction.atomic`), pero esta rama **nunca fue mergeada a `main`**. 19 commits con ~3,365 lineas de codigo funcional que no llegan al producto final. Esto es un problema serio de integracion.

## 3. API REST (Views y Serializers)

**Lo que esta bien:**
- Uso correcto de `generics.ListCreateAPIView` y `RetrieveUpdateDestroyAPIView` en publicaciones
- Permiso personalizado `EsCreadorOSoloLectura` para autorizacion a nivel de objeto
- Paginacion con `PageNumberPagination` (page_size=20, max=100)
- Filtros por busqueda, categoria, rango de precio y ordenamiento
- `select_related` y `prefetch_related` para optimizacion de queries (previene N+1)
- Patron soft delete en `destroy()` - cambia estado a 'cerrado' en vez de eliminar fisicamente
- Serializers diferenciados: `List` vs `Detail` vs `Create` - buena practica para rendimiento
- `CreadorResumenSerializer` vs `CreadorDetalleSerializer` - niveles progresivos de detalle
- `RegistroSerializer` con `@transaction.atomic` para crear usuario + perfil atomicamente
- `habilidad_ids` write-only con `habilidades` read-only - separacion limpia de lectura/escritura
- `foto_perfil_url` como `SerializerMethodField` construyendo URI absoluta
- Upload de imagenes con limite de 3 por publicacion
- `FormParser`, `MultiPartParser`, `JSONParser` configurados para manejar diferentes content types

**Que mejorar:**

### 3.1 Parametros de precio sin validacion
`publicaciones/views.py` lineas 52-58: los query params `precio_min` y `precio_max` se pasan directamente al filtro sin validar tipo numerico. Enviar un string no numerico causa un `ValueError` no manejado (error 500). Deberian envolver en `try/except` o usar `django_filters.FilterSet`.

### 3.2 `PerfilView.put()` usa `partial=True` que es semantica de PATCH
`usuarios/views.py` linea 42: el metodo `put` establece `partial=True`, lo cual es semantica de PATCH (actualizacion parcial), no de PUT (reemplazo completo). Deberian usar el metodo HTTP PATCH o no pasar `partial=True`.

### 3.3 `ExperienciaDetailView` usa APIView manual en vez de generics
`usuarios/views.py` lineas 74-99: maneja manualmente `try/except DoesNotExist` y los metodos `put`/`delete`. Usar `generics.RetrieveUpdateDestroyAPIView` con `get_queryset()` filtrado por usuario seria mas limpio y DRY.

### 3.4 Validacion de password incompleta en registro
`usuarios/serializers.py` linea 9: solo valida `min_length=8`. Los `AUTH_PASSWORD_VALIDATORS` de Django (similitud con atributos, contrasenas comunes, solo numeros) estan configurados en settings pero no se aplican en el serializer de registro. Se deberia llamar `validate_password()` de Django.

### 3.5 No hay DEFAULT_PERMISSION_CLASSES
`core/settings.py` lineas 145-149: `REST_FRAMEWORK` no define `DEFAULT_PERMISSION_CLASSES`. El default de DRF es `AllowAny`, lo que significa que cualquier nueva view sin permisos explicitos queda abierta. Mejor practica: defaultear a `IsAuthenticated` y hacer opt-out explicito para vistas publicas.

## 4. Frontend (Next.js + TypeScript)

**Lo que esta bien:**
- Arquitectura basada en features: `features/auth`, `features/services`, `features/profile` - excelente separacion de concerns
- Cada feature tiene su propio `models.ts`, `services/`, `hooks/`, `components/` - organizacion clara
- Patron adapter (`features/services/adapters.ts`) para transformar respuestas de API a props de componentes - desacopla forma del backend de la UI
- Custom hooks (`usePerfil`, `usePublicaciones`, `usePublicacion`, `useExperiencias`, `useHabilidades`) encapsulan logica de data fetching
- `AuthProvider` con `createContext` limpio: `login`, `logout`, `refreshPerfil`
- Next.js App Router con grupo de rutas `(protected)` usando guard de autenticacion en layout
- shadcn/ui para componentes de UI consistentes
- Biome para linting/formatting - herramienta moderna
- TypeScript con interfaces tipadas para todos los shapes de datos
- SignupWizard con pasos progresivos (datos basicos -> tipo de usuario -> bio)
- Debounce de 300ms en busqueda de servicios
- Estados de loading, error y empty manejados correctamente

**Que mejorar:**

### 4.1 No se usa el refresh token
`AuthContext.tsx`: el login recibe `access` y `refresh` tokens, pero solo guarda `access` en localStorage. El `refresh` token se descarta completamente. Cuando el access token expira (1 hora segun settings), el usuario es deslogueado silenciosamente. El endpoint `/api/auth/refresh/` existe pero nunca se llama desde el frontend. Se deberia implementar un interceptor que use el refresh token automaticamente.

### 4.2 Contratos y Dashboard usan datos hardcodeados
- `features/contracts/data.ts`: 4 contratos mock con datos en ingles ("Enterprise E-commerce Platform Redesign", "Sarah Jenkins")
- `features/dashboard/dashboard.tsx` lineas 14-72: `SERVICES` y `CONTRACTS` son constantes hardcodeadas, no se obtienen de la API
- `features/dashboard/components/RecommendedServices.tsx` linea 86: `<Link href="/services/1">Contratar</Link>` hardcodea el link a `/services/1` para TODOS los servicios recomendados

### 4.3 Inconsistencia de idioma
Los contratos estan completamente en ingles mientras el resto de la app esta en espanol:
- `ContractHeader.tsx`: "Active Contracts", "Review and manage...", "+ Post a Job"
- `ContractFilters.tsx`: "Search by project, client, or keyword..."
- `ContractCard.tsx`: "Client", "View Details"
- `ContractList.tsx`: "Show Archived Contracts"

Esto sugiere que la seccion de contratos fue copiada de un template sin traducir.

### 4.4 Filtros no funcionales en ServiceFilters
`components/ServiceFilters.tsx` lineas 101-121: las secciones "Tiempo de Entrega" y "Calificacion" se renderizan pero no llaman `onFilterChange` y no tienen soporte en el backend. El filtro "mejor-calificados" mapea a `-created_at` (igual que "nuevos") porque no hay sistema de calificaciones.

### 4.5 Uso de `<img>` en vez de `<Image>` de Next.js
`ServiceCard.tsx`, `ServiceGallery.tsx`, `CreateServiceForm.tsx`: usan tags `<img>` directamente en vez del componente `<Image>` de Next.js, perdiendo optimizacion de imagenes (lazy loading, formatos modernos, responsive sizes).

### 4.6 Tipo `Perfil` duplicado
`features/auth/models.ts` define un `Perfil` que es un subset de `features/profile/models.ts`'s `PerfilCompleto`. Dos tipos diferentes para el mismo concepto, el de auth no tiene `habilidades` ni `experiencias`.

## 5. Docker e Infraestructura

**Lo que esta bien:**
- Arquitectura de 3 servicios (db, backend, frontend) con red dedicada `marketplace`
- PostgreSQL con healthcheck via `pg_isready`
- Backend con `depends_on: condition: service_healthy` - espera a que la DB este lista
- Volume nombrado `pgdata` para persistencia de datos
- Volumes anonimos `/app/node_modules` y `/app/.next` para evitar conflictos con host
- `entrypoint.sh` corre migraciones y seed de habilidades automaticamente
- `.env` variables para configuracion de base de datos

**Que mejorar:**

### 5.1 SECRET_KEY insegura en produccion
`core/settings.py` linea 29: tiene un `SECRET_KEY` default inseguro hardcodeado. El `docker-compose.yml` NO establece `SECRET_KEY`, asi que se usa el default inseguro en Docker. Deberia ser una variable de entorno obligatoria.

### 5.2 Servidor de desarrollo en Docker
`backend_marketplace/Dockerfile`: usa `python manage.py runserver` como CMD. El `pyproject.toml` incluye `gunicorn==25.0.3` pero nunca se usa. `runserver` es el servidor de desarrollo de Django y no deberia usarse en produccion.
`frontend_marketplace/Dockerfile`: usa `bun run dev` en vez de `bun run build && bun run start`.

### 5.3 No hay `.dockerignore` en backend ni frontend
Archivos innecesarios como `uv.lock`, `demo_data.sql`, `node_modules` locales se copian a las imagenes Docker.
